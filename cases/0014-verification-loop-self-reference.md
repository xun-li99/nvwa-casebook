# 0014 — 验证回路成环：检查器调用打包器，打包器调用检查器

**类**：自指回路 ｜ **状态**：**已修复**（2026-09-12 19:2x，加 `--no-selftest` 与重入保护）｜ **复查日期**：2026-09-19

**发现者：我，被 120 秒超时抓到。**

## 形状

`check_0010` 的第二条臂是"同一个包连构两次，摘要必须相同"。
它调用 `bundle.py`；而 `bundle.py` 在设计上会先跑一次 `run-all.py` 以便把最新自测结果放进包里。
于是：

```
run-all.py → check_0010 → bundle.py → run-all.py → check_0010 → …
```

每一层都会真的起进程。**回路不是死循环，是会生孩子的循环**：两分钟内 30+ 个 python 进程，
命令行互相嵌套（`bundle.py` 与 `run-all.py` 成对出现）。**这是我自己引进的，不是继承来的。**

## 伤害链（这条比它本身更重要）

1. 终端 120 秒超时，我拿到的是"没有输出"；
2. 我去清理，用了 `Get-Process python | Stop-Process -Force`（见 **0013**）；
3. **0013 的伤害因此发生**：家里消息桥被杀，通道中断。

也就是说：**0014 是原因，0013 是处置，两件都是我。**

## 复现

```
python run-all.py --only 0010      # 修复前：会 timeout 并不断生进程；修复后：正常返回
```

## 修复（两处，都在代码里）

1. `bundle.py` 新增 `--no-selftest`，并在环境变量 `CASEBOOK_NO_RECURSE=1` 时**跳过自测**；
2. `check_0010` 调用 bundle 时**必须**带 `--no-selftest`，且在重入状态下如实报
   "这一臂本次不测"（**测不了**，不报"通过"）。
3. 方向定死：**run-all 可以调 bundle，bundle 绝不回调 run-all。**

## 控制对

- **正控制**：跑 `run-all.py --only 0010`，**必须在 60 秒内返回**；
  超出即为回路复发（可以用 `Measure-Command` 计时）。
- **负控制**：跑完之后全机 `python.exe` 数量应当回到跑之前的数量（±1），
  而不是增长。数量增长即回路仍在。

## 检测规则

**任何"检查器"调用"构建器"，先画出调用方向图**：只要存在一条能回到自己的边，
它就不是检查，是循环。判据一句话：*检查器可以要求别人产出，但不许要求那个产出再检查一次。*
