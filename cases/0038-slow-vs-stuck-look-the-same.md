# 0038 — 跑得慢、卡住了、没在跑：从外面看是同一个读数

**类**：沉默被读成正常（0022 / 0025 家族）｜ **状态**：部分修复 ｜ **复查日期**：2026-09-28

**发现者：我，2026-09-21 晚上——而且是在我**连续误诊两次**之后才发现的。**

## 形状

一个"要跑很久"的东西，在跑的过程中**什么都不输出**。于是从外面看：

- **它跑得慢**（世界正常，只是慢）；
- **它卡死了**（我的进程被一个不返回的调用扣住）；
- **它根本没在跑**（早就死了，或者我杀错了进程）。

三个世界，观测者这一侧印出来是**同一行缺席**。这就是 0022（静默被信任）与 0025
（"启动了"被读成"在跑"）的同一个病，长在**运行器自己**身上：我的自测套件从不报告进度。

## 实例（本机，可核）

2026-09-21 19:03 起跑全量自测，日志 `C:\Users\Mechrevo\Desktop\璃\full-run-0921.log`。
**19:05 到 19:10 之间该文件一直停在 7,682 字节**，最后一行是 0014 的最后一支臂。
我在这段时间里做了两次诊断，**两次都没有证据**：

1. 第一次："卡死在 0015。" —— 依据只是"日志停在 0014 之后"。**这是猜的。**
2. 第二次："是另一个 run-all 在抢网络。" —— 依据是进程表：18:53 那次**超时的工具调用**
   在超时后**把子进程留在了世上**（pid 41756 / 33568，19:05 我先杀掉它们）。这一条**有证据**，
   但它仍然不能推出"就是它导致了停滞"。

随后单独跑那一条：`python run-all.py --only 0015` → **53.9 秒**，状态 `测不了`
（`/api/v1/faucet=ERR:URLError`、`/api/v1/earn=ERR:URLError`、另两条正常回 404）。
同一天还有独立证据说明当时网络确实差：Superteam 那条腿 urllib 报 `SSL: UNEXPECTED_EOF_WHILE_READING`
（见 0028 第二实例），0006 的活臂当时印出的是 `解包 reason='net:SSLEOFError'`。

**所以真相大概率是两件事叠加**（网络差 ＋ 三个进程同时打网络），
但"卡死"这个结论**我从来没有验证过**——它是猜的，而且它当时听起来像读数。

## 复现

```
python run-all.py --only 0006 --budget 0     # 正控制：必须印"预算用完"并退出 3
python run-all.py --only 0006                # 负控制：必须退 0，且案卷行尾带 [n.ns]
```

`check_0038` **跑**这两臂（都走 `spawn()`，见 0014 的成环教训）：
预算臂没有那行字、或退出码不是 3 ⇒ 仍复现；对照臂没有秒数、或退出码不是 0 ⇒ 仍复现。

## 控制对

- **正控制**：`--budget 0` —— 必须有东西**亮**（`‖ 预算 0 秒用完…这不是通过，也不是卡住，是没跑`）且退出码 3。
- **负控制**：同一条 check 不带预算 —— 必须**不亮**，退出 0，且行尾有耗时。
  没有负控制就分不清"预算真的生效"与"这个运行器见了谁都印这句话"。

## 地基（不经检验就信任的东西）

1. **`print(..., flush=True)` 真的把字节送出去了**——管道／重定向下不缓冲。这一条我**没有**验证过，
   它由 Python 的 `flush` 语义构造信任。
2. **`time.time()` 的差值可用**。墙上时钟可以被回拨／同步，我只用它做差值。
3. **`subprocess.run` 会阻塞到子进程结束**（`check_0038` 的两臂靠这个才叫控制对）。
4. **哪一条 check 该跑多久由外部世界决定**：0015 要打外网，它今天 53.9 秒、明天可能 5 秒或 300 秒。
   本条的判据因此**不许**建立"某条 check 应在 N 秒内跑完"上。

**上次确认这个信任仍然成立：2026-09-21**（两条臂当天都跑过：预算臂退 3、对照臂退 0）。

## 检测规则

> **一个要跑很久的东西，必须在开跑前说出"我在跑哪一条"，在跑完后说出"我用了多久"；
> 并且"没跑"要是一个**独立的第三种状态**——不是通过，也不是卡住。**
> 把"预算用完"印成 0 条案卷的汇总，等于让"我没跑"冒充"世界没问题"。

## 修复（已上线四件）

1. 每条 check **开跑前**先印一行 `… 0015`（带 `flush`）⇒ 卡住时日志的最后一行就是答案。
2. 每条结果行尾带 `[53.9s]`。
3. `--budget 秒`：到点停，**印出还剩哪些没跑**，退出码 **3**（与 `--strict` 的 1 分开）。
4. **被预算截断的一轮不许写全量台账**，`--json` 也降级成 `last-run-budget.json` 并在载荷里带
   `budget_truncated`。否则"我只跑了一半"会冒充"世界的状态"——2026-09-13 那次
   `--only 0013 --json last-run.json` 把它覆盖成 1 条，是同一个病。

## 洞（不装补上）

**预算只在两条 check 之间检查。**所以一条**卡在里面的** check 会让检查点永远到不了——
上面那个"停滞 >5 分钟"的场景，**今天这一版仍然治不了**。
真正的修法是给每条 check 一个看门狗（子进程 ＋ 超时，或线程 ＋ 超时），
而这两条都会碰到既有设计：0036 的臂③要求在**本进程内**核写盘函数，
所以"每条都塞进子进程"这条直路走不通。**记在这里，不假装修了。**
