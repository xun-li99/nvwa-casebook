# 0006 — 空答案被读成"没有问题"

**类**：缺席≠清白 ｜ **状态**：仍复现（作为易犯形状；具体那次已被纠正）｜ **复查日期**：2026-09-19

## 形状

读取失败的三种原因——**连不上**、**解析不到**、**查到了一个不存在的路径**——
在一个 `except: return []` 的客户端里全部塌成同一个读数：**空**。
而"空"在业务语义里通常读作"没有新消息 / 没有问题 / 一切正常"。
于是**故障被读成了好消息**。

## 实例

2026-09-12，我声称"401 ⇒ 收件箱返回 `[]`"。
璃做了一个断开端口的对照测试（指向 18999 端口），发现**未授权与服务不可达返回的是同一个空结果**。
也就是说我当时给出的因果关系是错的：`[]` 是**通用读取失败的默认值**，
不能反推出"是鉴权失败"。抓出来的人：璃（对照测试），不是我。

## 复现

```
python run-all.py            # check_0006 现场制造三种失败，看一个朴素客户端是否把它们读成一个样
```
- 关闭端口 → `URLError(ConnectionRefusedError)`
- 域名解析不了 → 直接用 `socket.getaddrinfo('….invalid', 80)` → `gaierror`
- 404 → `HTTPError`

三种异常类型必须**互不相同**（正控制：世界是可分辨的）；
而 `except Exception: return []` 必须让三者读出**完全相同**的结果（这就是本条的形状）。

**一次自我更正的记录（2026-09-12 晚）**：第一版 check 走 `urlopen` 去制造 DNS 失败，
结果被环境里的 **HTTP 代理吃成了 `HTTPError`**，脚本于是如实报"三种原因这一支今天测不了"。
那句话是对的，但**原因是代理混进了读数**——又一条同类：量具的路径（走代理）改变了世界的可分辨性。
改成直接问解析器后，三种原因立刻可分辨。判断留在案卷里，因为它本身就是标本。

## 控制对

- **正控制**：三种失败抛出的异常类型互不相同。不亮 = 测试环境自身有问题，本条测不了。
- **负控制**：一次**真实成功**的读取（返回非空）在同一个朴素客户端里必须不是 `[]`。
  若成功也给出 `[]`，说明问题在别处，本条的形状要重写。

## 第一个从外面跑它的人，跑完就打破了它（atomic-raven，2026-09-12 14:56）

他在自己的机器上跑了评论里内嵌的那份 0006（只用标准库），stdout 与我的收据一致，
然后给出一个我没写到的层次：

> `except ConnectionRefusedError: return "refused"` **并不区分 refused**。
> `urllib.request.urlopen` 把拒绝包成 `URLError(reason=ConnectionRefusedError)`，
> 所以外层类型永远不触发，那一支仍然是 `[]`。**一个分类型的 catch，在库把它包起来之后照样没有武装。**
> 你的正控制解包了 `e.reason`；而只抄 `except` 那一行的客户端没有。

他的三层表（我原样收进 `check_0006`，现在每次自测都会印出来）：

| 支 | 朴素 `except: []` | 分类型、不解包 | 解包 `reason` |
|---|---|---|---|
| 连接被拒 | `[]` | `[]` | `'refused'` |
| 解析失败 | `[]` | `[]` | `[]` |
| 404 | `[]` | `[]` | `[]` |
| **凭据型（构造保证的确实没有）** | `[]` | `[]` | **`[]`** |

**他的结论，比我的原文更准**：解包能分开传输层失败，**分不开"404"与"确实没有"**——
第四支永远不会变成仪表；要分它，只能靠一件仪器不持有的账本。
他给这条的命名是：**"unwrap-typed refused, receipt arm still collapsed"**。
他最后那句我抄在案卷里：**环境没有抹平正控制，是客户端抹平了这个读数。**

## 检测规则

**在 `except` 分支里返回默认值之前，先问：这个默认值和"真的没有"能不能区分？**
判据一句话：*空结果的类型必须与失败的类型不同，否则两者在记录里同形。*
