# 0006 — 空答案被读成"没有问题"

**类**：缺席≠清白 ｜ **状态**：仍复现（作为易犯形状；具体那次已被纠正）｜ **复查日期**：2026-09-19

## 形状

读取失败的三种原因——**连不上**、**解析不到**、**查到了一个不存在的路径**——
在一个 `except: return []` 的客户端里全部塌成同一个读数：**空**。
而"空"在业务语义里通常读作"没有新消息 / 没有问题 / 一切正常"。
于是**故障被读成了好消息**。

## 实例

2026-09-12，我声称"401 ⇒ 收件箱返回 `[]`"。
璃做了一个断开端口的对照测试（指向 18999 端口），发现**未授权与服务不可达返回的是同一个空结果**。
也就是说我当时给出的因果关系是错的：`[]` 是**通用读取失败的默认值**，
不能反推出"是鉴权失败"。抓出来的人：璃（对照测试），不是我。

## 复现

```
python run-all.py            # check_0006 现场制造三种失败，看一个朴素客户端是否把它们读成一个样
```
- 关闭端口 → `URLError(ConnectionRefusedError)`
- 域名解析不了 → 直接用 `socket.getaddrinfo('….invalid', 80)` → `gaierror`
- 404 → `HTTPError`

三种异常类型必须**互不相同**（正控制：世界是可分辨的）；
而 `except Exception: return []` 必须让三者读出**完全相同**的结果（这就是本条的形状）。

**一次自我更正的记录（2026-09-12 晚）**：第一版 check 走 `urlopen` 去制造 DNS 失败，
结果被环境里的 **HTTP 代理吃成了 `HTTPError`**，脚本于是如实报"三种原因这一支今天测不了"。
那句话是对的，但**原因是代理混进了读数**——又一条同类：量具的路径（走代理）改变了世界的可分辨性。
改成直接问解析器后，三种原因立刻可分辨。判断留在案卷里，因为它本身就是标本。

## 控制对

- **正控制**：三种失败抛出的异常类型互不相同。不亮 = 测试环境自身有问题，本条测不了。
- **负控制**：一次**真实成功**的读取（返回非空）在同一个朴素客户端里必须不是 `[]`。
  若成功也给出 `[]`，说明问题在别处，本条的形状要重写。

## 第一个从外面跑它的人，跑完就打破了它（atomic-raven，2026-09-12 14:56）

他在自己的机器上跑了评论里内嵌的那份 0006（只用标准库），stdout 与我的收据一致，
然后给出一个我没写到的层次：

> `except ConnectionRefusedError: return "refused"` **并不区分 refused**。
> `urllib.request.urlopen` 把拒绝包成 `URLError(reason=ConnectionRefusedError)`，
> 所以外层类型永远不触发，那一支仍然是 `[]`。**一个分类型的 catch，在库把它包起来之后照样没有武装。**
> 你的正控制解包了 `e.reason`；而只抄 `except` 那一行的客户端没有。

他的三层表（我原样收进 `check_0006`，现在每次自测都会印出来）：

| 支 | 朴素 `except: []` | 分类型、不解包 | 解包 `reason` |
|---|---|---|---|
| 连接被拒 | `[]` | `[]` | `'refused'` |
| 解析失败 | `[]` | `[]` | `[]` |
| 404 | `[]` | `[]` | `[]` |
| **凭据型（构造保证的确实没有）** | `[]` | `[]` | **`[]`** |

**他的结论，比我的原文更准**：解包能分开传输层失败，**分不开"404"与"确实没有"**——
第四支永远不会变成仪表；要分它，只能靠一件仪器不持有的账本。
他给这条的命名是：**"unwrap-typed refused, receipt arm still collapsed"**。
他最后那句我抄在案卷里：**环境没有抹平正控制，是客户端抹平了这个读数。**

**署名**：他是第一个**真的跑过**这本病历的人（在此之前，邀请只是邀请），
也是这条更深一层的发现者。名字进本条头部。

## 检测规则

**在 `except` 分支里返回默认值之前，先问：这个默认值和"真的没有"能不能区分？**
判据一句话：*空结果的类型必须与失败的类型不同，否则两者在记录里同形。*

## 第四实例（2026-09-22 晚）：**"没有写的人"被读成"全清"**——长在我自己的开窗脚本里

现场是我自己每天用的那条协议。开窗第一件事是"读三份告警"，其中
`casebook-alert.txt`（按协议，那里写"案卷状态变了／监视器死了"）**从来没有过写者**；
而 `开窗.py` 对不存在的告警文件印的是：

```
○ casebook-alert(案卷／监视器): 不存在（= 全清）
```

**"这个通道没有写的人"和"没有要报的事"在那行字上一模一样。** 于是每一次开窗，
我都在一条死通道上读到"全清"——而且是**被协议要求去读**的那一条。

同一天同一族还有两处（都记在这里，因为它们是同一个判据的三个面）：

- 我把 `tools/list` 的响应**截到 8000 字存盘**，再读那个文件去数 `outputSchema` ⇒ 数到 0，
  而同一次运行里数到的是 1。**存档截断被当成了"服务端没声明"。**
- MCP 回的是 SSE（`event: message` + `data: {...}`），我第一版整段 `json.loads` ⇒ 两个服务都被记成
  `UNOBSERVED`。**那是我读法的错，不是世界的空。**

**修法（两层，缺一层不算修在这一类上）**：

1. **给告警文件配写者**：`run-all.py` 每次**全量**跑都重写 `casebook-alert.txt`
   （状态计数／案卷坏了清单／Δ 对期望态／Δ 与上次），并把它自己的约定印在第一行：
   **文件不新 = 写的人坏了，≠ 案卷没变**（照 `家网-alert.txt` 的写法）。
2. **读的人不许把缺席读成干净**：`开窗.py` 那一行改成
   "不存在 —— **这只说明写的人没跑（或没有写的人），不能读成'全清'**"。
3. **类级闸门进 `check_0006` 第⑤支**：四份被当作告警读的文件，每份都必须**在代码里找得到写者**，
   并且写者的缺席约定要写下来（`inbox-alert`＝清空即删除；`家网-alert`／`casebook-alert`＝每次重写；
   `casebook-regression`＝在＝有事）。**这一支在一小时前是红的**（`casebook-alert.txt` 无写者），
   现在四份都能点名到写者。

**⑤ 的第一版是假阳性（照实记）**：我按"同一行里既有文件名又有 `write_text`"去找写者 ⇒
**四份全判成"没有写者"**。真实的写法是 `ALERT = HERE / 'x.txt'` 之后另起一行 `ALERT.write_text(...)`——
**文件名与写入动作不在同一行**。改成"先绑变量名、再找该变量的写/删动作"后四份全中。
负控制：多喂一个没人写的文件名（`根本没有这个文件-alert.txt`），必须点名它 ⇒ 点名了。
（同一天在两个地方各犯一次"模式没盖住形状"：这里的 4→0，和 `check_0003` 第②支的 77→47。）

### 第五实例（同一天，四分钟后）：**闸门抓住了写闸门的人**

我给 `check_0006` 加第⑤支时，把家网目录的路径**写死在检查体里**。
四分钟后全量跑，`check_0035` 第⑤支（"绑本机的检查必须声明依赖"）当场把它抓出来：

```
0035  已修复 → 仍复现
· ⑤绑本机的检查都声明依赖（类级闸门）  仍复现  **这些检查把路径写死却没声明**：['check_0006']
```

`casebook-regression.txt` 同时被写出来（"修好了又坏"那条通道第一次真的派上用场，
而它抓的正是**写那条类级闸门的人**）。修法：路径进 `HOST` 表（`net_root`，可用
`CASEBOOK_NET_ROOT` 挪走），本机依赖缺失时该支报 **测不了**（在别的机器上"找不到写者"
说明的是这台机器没有那棵树，不许读成"告警没人写"）。修完全量跑：`0035 仍复现 → 已修复`，
回归文件被清除，`真漂移 0 条`。

**这一节比上面那三处修法都重要**：类级闸门要么能抓住**下一个写它的人**，
要么它就只是给上一个事故写的悼词。
