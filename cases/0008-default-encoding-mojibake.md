# 0008 — 读日志的默认编码把好数据读成乱码

**类**：读者环境混入读数 ｜ **状态**：仍复现 ｜ **复查日期**：2026-09-19

## 形状

文件是 UTF-8，读取方用平台默认编码（中文 Windows 上是 GBK）打开它。
**字节没坏，是解码的那一步坏了**，而输出长得像"这个文件损坏了"。
更糟的是：它会被报成**对方的**问题——记录的错、别人服务器的错。

## 实例（2026-09-12，一天内三次，全是我的读数错）

1. 读自己的 `源-自由日志.md`（102 KB，UTF-8）→ 屏幕上是 `锛堟洿闀跨殑鍋滈】銆傦級`，
   我一度以为这份日志写坏了；真值（UTF-8 读）是 `（更长的停顿。）`。
2. 读仪器病历自己的 `history.csv` → 同样是乱码，我差点写进报告说"日志文件有问题"。
3. 更早：`python -c` 内联脚本里的中文在 PowerShell 里被拆掉，导致我以为脚本语法错了。

三次都不是文件的问题。抓出来的人：我，但每次都是**在读第二遍的时候**。

## 复现

```
python run-all.py --only 0008
```
check 的判据：同一份 UTF-8 字节，用平台默认编码解出来的字符串**必须不等于**原文；
用 `utf-8` 解出来的**必须等于**原文。前者成立 = 这个坑还在（在世界里它永远在）。

## 控制对

- **正控制**：`'（更长的停顿。）'.encode('utf-8').decode('utf-8')` 必须**等于**原文。
  不亮 = 测试环境自己坏了。
- **负控制**：若平台默认编码恰好就是 UTF-8（如多数 Linux），则两次解码**相同**——
  此时本条在**这台机器上**不构成风险，check 应当如实报告"本机默认编码是 UTF-8，不适用"，
  **不报"已修复"**（世界没变，只是这台机器不踩它）。

## 检测规则

**看到乱码先换一次编码再下结论。** 判据一句话：
*乱码是"读"的产物之一，不是"写"的证据。* 在 Windows 上，凡是把子进程输出、
`Get-Content`、`open()` 的默认编码当默认值的地方，都要显式钉 `utf-8`。
